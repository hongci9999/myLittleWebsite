# 링크드인 포스트 초안

이미지 순서: ① architecture.png ② results.png ③ example.png

---

개인 사이트의 AI 검색에 벡터 RAG를 붙이고, 붙이기 전과 후를 측정해 봤습니다.

제 사이트에는 그동안 모아 둔 AI 도구·칼럼·게임 개발 자료 200여 건이 있고, 화면 하단 대화창(과 MCP 서버)에 물어보면 AI가 찾아 줍니다. 원래 방식은 단순했습니다. LLM이 자료 목록(제목·요약·태그, 약 3만 토큰)을 통째로 받아서 질문에 맞는 걸 직접 고릅니다. 임베딩도 벡터DB도 없는, 도구 호출형(agentic) RAG입니다.

"유니티 관련 뭐 있어?" 같은 질문에는 이게 충분했습니다(정답률 97%). 문제는 "pgvector 쓰는 자료 있어?"처럼 제목·요약에는 없고 README나 영상 자막 속에만 있는 내용이었습니다. 목록만 보는 LLM은 찾을 방법이 없어서, 이름이 비슷한 "PostgreSQL MCP 서버"를 짐작으로 내놨습니다.

그래서 기존 방식을 바꾸지 않고 더하기로 했습니다.
· 어느 자료인지 → 지금처럼 LLM이 목록에서 고른다
· 자료 안 어디인지 → 원문(자막·README·웹 글)을 1,000자 조각으로 나눠 Gemini 임베딩 + Supabase pgvector로 검색한다
· 두 도구를 같은 회차에 병렬로 부른다. 질문 유형을 모델이 판단해서 하나를 고르게 하면, 판단이 빗나갈 때 통째로 틀리기 때문입니다

구현 전에 측정 도구부터 만들었습니다. 붙이고 나면 "전" 수치는 다시 잴 수 없으니까요. 원문 속 질문 11개는 DB에서 "원문에는 있는데 제목·요약·태그에는 없는 키워드"를 뽑아 문맥을 확인하고 만들었고, 자료 찾기 질문 10개와 합쳐 21개를 3번씩 돌렸습니다.

결과 (같은 모델 Gemini 3.1 Flash-Lite)
· 원문 속 질문, 정답 자료를 1개 이상 찾음: 33% → 82%
· 자료 찾기 질문: 97% → 100%
· 대가: 응답 시간 +0.9초(중앙값 2.9 → 3.8초), 입력 토큰 +2.5%

처음부터 이렇게 나오진 않았습니다. 1차 측정에서 원래 잘 되던 자료 찾기 회수율이 94% → 83%로 떨어졌습니다. 답변을 열어 보니, 원문 조각이 들어오자 모델이 자료를 넓게 나열하던 답을 한 자료를 깊게 설명하는 답으로 바꿔 버렸더군요. "관련 자료는 빠짐없이 나열하고, 조각은 근거 한 줄로만"이라는 규칙을 넣어 87~89%까지 되돌렸습니다. 측정을 안 했다면 정답률이 오른 숫자만 보고 넘어갔을 겁니다.

토큰도 처음엔 +15%였습니다. 원문 조각 8개가 더 들어가니 당연하다고 생각했는데, 기존 목록을 뜯어보니 항목마다 사이트 전체 주소가 207번 반복되며 목록의 25%를 차지하고 있었습니다. 도메인은 한 번만 알려 주고 경로만 넣었더니, 조각을 더하고도 구현 전 대비 +2.5%로 끝났습니다. 정확도는 그대로였고요.

남은 약점도 분명합니다. "Tauri로 만든 도구"처럼 정확한 고유명사는 벡터 검색이 뜻이 비슷한 Electron 문서를 먼저 올립니다. 다음 단계는 키워드 검색(BM25)을 섞는 하이브리드입니다.

정리하면
1. 자료 수백 건 규모라면 "LLM이 목록을 통째로 보고 고르기"는 생각보다 강하다. 벡터 RAG는 대체가 아니라 그 빈칸(원문 속 내용)을 메우는 용도였다.
2. 기능을 더하면 원래 되던 게 망가질 수 있다. 전후를 같은 질문으로 재야 보인다.
